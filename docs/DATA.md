База і історія

База даних

MySQL 8.4 на RDS (db.t4g.micro) у приватних підмережах, з інтернету вона недоступна. З'єднання дозволені тільки від функцій (порт 3306). Інфраструктура в terraform/database.tf і network.tf. Пароль генерує Terraform.

Таблиця

Одна таблиця measurements для всіх датчиків:

- sensor_id: ідентифікатор датчика
- measured_at: час вимірювання в UTC, з мілісекундами
- sensor_type: temperature, humidity, light або camera
- value: значення після обробки (для камери розмір знімка в байтах)
- unit: одиниця виміру
- lat, lon: координати датчика
- status: ok, out_of_range або anomaly
- note: пояснення до статусу, або NULL
- object_key: ключ знімка в S3 (тільки для камери), інакше NULL

Первинний ключ: (sensor_id, measured_at).

Чому одна таблиця

У всіх типів датчиків однакові поля (датчик, час, число, одиниця, координати), а запити завжди йдуть за датчиком і часом. Новий тип датчика не треба додавати в схему. Окремі таблиці мали б сенс, якби типи сильно відрізнялись. Камера відрізняється тільки одним полем, тому я додала колонку object_key, а не окрему таблицю.

Індекс

Первинний ключ (sensor_id, measured_at) одночасно є індексом. Запит історії читає потрібний проміжок у вже відсортованому порядку, без окремого сортування. Цей самий ключ захищає від дублів (див. docs/PROCESSING.md).

Читання історії

GET /sensors/{sensor_id}/history

Параметри, усі необов'язкові: from і to (UTC, ISO 8601), limit (від 1 до 1000, за замовчуванням 100), source (sql або nosql, за замовчуванням sql, див. docs/NOSQL.md). Потрібен заголовок x-api-key.

Відповідь: масив від нових вимірювань до старих, порожній масив якщо даних нема. Помилки: 400 при неправильних from, to, limit або source, 401 без правильного ключа. Для камери в кожному записі є ще object_key і image_url, це посилання на знімок на 5 хвилин (docs/BLOB.md).

Приклад:

```
curl -s -H "x-api-key: $KEY" "$API/sensors/temp-01/history?limit=2"
```

```
[
  {
    "sensor_id": "temp-01",
    "sensor_type": "temperature",
    "value": 27.28,
    "unit": "C",
    "location": { "lat": 50.4501, "lon": 30.5234 },
    "measured_at": "2026-11-19T19:36:59.270Z",
    "status": "ok",
    "note": null
  }
]
```

Як функції підключаються до бази

Функції processor і history стоять у приватних підмережах тієї самої мережі, що й база. Адреса, користувач і пароль бази передаються їм як змінні середовища, їх задає Terraform. Інтернет-шлюзу і NAT нема, вони не потрібні: чергу читає сама служба Lambda, а решту робить база. Таблиця створюється при першому запуску через CREATE TABLE IF NOT EXISTS. З'єднання відкривається один раз на середовище функції і далі використовується повторно.

Обмеження на кількість з'єднань

База витримує обмежену кількість з'єднань (для db.t4g.micro близько 85). Кожне запущене середовище функції тримає одне з'єднання. Якщо повідомлень дуже багато, функцій запускається багато, і база може почати відповідати Too many connections. Тому:

- тригер від черги має ліміт 5 одночасних запусків (maximum_concurrency), тобто не більше 5 з'єднань;
- у кожного середовища пул з одного з'єднання (connectionLimit: 1);
- запити через шлюз обмежені лімітом шлюзу.

Для більшого навантаження ставлять RDS Proxy, який об'єднує багато з'єднань функцій у кілька до бази, або беруть сховище без такого ліміту, наприклад DynamoDB.

Секрети

Пароль бази і ключ API передаються функціям як змінні середовища, у репозиторії їх немає. У справжній системі пароль краще тримати в Secrets Manager, але для цього потрібні додаткові приватні ендпоінти або NAT, а вони коштують грошей, тому для лабораторної вибрано простіший варіант.
