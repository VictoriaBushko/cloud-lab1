Черга недоставлених повідомлень (DLQ)

Налаштування

У основної черги cloud-lab3-measurements є політика redrive: після 3 невдалих спроб (maxReceiveCount = 3) повідомлення само переходить у чергу cloud-lab3-measurements-dlq. Там воно лежить 14 днів. Між спробами повідомлення невидиме 60 секунд, тому весь шлях до DLQ займає близько 3 хвилин. Налаштовано в terraform/queue.tf.

Processor повертає в чергу тільки ті повідомлення пачки, які не вдалося обробити (ReportBatchItemFailures). Решта пачки підтверджується і видаляється.

Перевірка

1. Надіслала в чергу повідомлення, яке не є JSON:

```
aws sqs send-message --queue-url $QUEUE --message-body 'not-json' --region eu-central-1
```

2. Одразу запустила емулятор на 20 секунд: 810 повідомлень, усі прийняті, errors=0.

3. У журналі processor з'явилась помилка для зіпсованого повідомлення:

```
failed ef0bf902-954d-444e-83a7-63b9df991ea6 Unexpected token 'o', "not-json" is not valid JSON
```

Далі в журналі йдуть звичайні рядки (processed:5, processed:9, processed:10), тобто обробка не зупинилась.

4. Через 3-4 хвилини повідомлення було в DLQ:

```
aws sqs get-queue-attributes --queue-url $DLQ --attribute-names ApproximateNumberOfMessages --region eu-central-1
```

Результат: ApproximateNumberOfMessages = 1.

Переглянути повідомлення в DLQ:

```
aws sqs receive-message --queue-url $DLQ --region eu-central-1
```

Навіщо потрібна DLQ

Без неї зіпсоване повідомлення поверталось би в чергу знову і знову, поки не мине термін зберігання (доба), і марно витрачало б запуски функції. З DLQ воно одразу відкладається окремо, і його можна розібрати.

Хто і як розбирає

Чергу розбирає власник системи, тобто той, хто підтримує конвеєр. Щоб не пропустити проблему, на DLQ варто поставити сигнал CloudWatch на метрику ApproximateNumberOfMessagesVisible (більше нуля) з листом на пошту.

Порядок такий:

1. Подивитися повідомлення (aws sqs receive-message).
2. Знайти причину в журналі функції за ідентифікатором повідомлення.
3. Виправити код або дані.
4. Повернути повідомлення в основну чергу через redrive у консолі SQS, а якщо дані безнадійні, видалити.
