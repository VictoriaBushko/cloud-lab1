Черга недоставлених повідомлень (DLQ):

Що налаштовано:

Основна черга cloud-lab3-measurements має політику redrive: після 3 невдалих спроб обробки (maxReceiveCount = 3) повідомлення автоматично переміщується в чергу cloud-lab3-measurements-dlq. У DLQ повідомлення зберігаються 14 днів. Між спробами повідомлення невидиме 60 секунд (visibility timeout), тому весь шлях до DLQ займає приблизно 3 хвилини. Налаштування в terraform/queue.tf. Функція повертає тільки ті повідомлення пачки, які не вдалося обробити (ReportBatchItemFailures), решта пачки підтверджується.

Перевірка на некоректних даних:

1. У чергу напряму надіслано повідомлення, яке не є JSON:
   aws sqs send-message --queue-url $QUEUE --message-body 'not-json' --region eu-central-1
2. Одразу після цього емулятор 20 секунд надсилав звичайні дані (810 повідомлень, усі прийняті, errors=0).
3. У журналі функції processor видно помилку для зіпсованого повідомлення:
   failed ef0bf902-954d-444e-83a7-63b9df991ea6 Unexpected token 'o', "not-json" is not valid JSON
   Одразу за нею й далі функція обробляє решту повідомлень (processed:5, processed:9, processed:10 і так далі), тобто обробка не зупиняється.
4. Приблизно через 3-4 хвилини повідомлення опинилося в DLQ:
   aws sqs get-queue-attributes --queue-url $DLQ --attribute-names ApproximateNumberOfMessages --region eu-central-1
   Результат: ApproximateNumberOfMessages = 1.

Як переглянути повідомлення в DLQ:

aws sqs receive-message --queue-url $DLQ --region eu-central-1

Що робити з такими повідомленнями:

Розібрати причину (за журналом функції), виправити код або дані і повернути повідомлення в основну чергу (redrive у консолі SQS) або видалити. Без DLQ таке повідомлення поверталося б у чергу, поки не спливе термін зберігання (24 години), і витрачало б виклики функції.

Хто і як розбирає чергу:

Чергу недоставлених повідомлень розбирає власник системи (розробник, який підтримує конвеєр). Щоб не пропустити проблему, на DLQ слід налаштувати сигналізацію CloudWatch на метрику ApproximateNumberOfMessagesVisible більше нуля з повідомленням на пошту. Порядок розбору: переглянути повідомлення (aws sqs receive-message), знайти причину в журналі функції за ідентифікатором повідомлення, виправити код або дані, повернути повідомлення в основну чергу через redrive у консолі SQS або видалити його, якщо дані безнадійні.
