Обробка даних функціями:

Потік даних:

1. Емулятор надсилає вимірювання на приймач (API Gateway і функція ingest), який кладе їх у чергу SQS cloud-lab3-measurements.
2. Черга запускає функцію processor (код у functions/worker/processor.js). Пачками до 10 повідомлень, з паралелізмом не більше 5 одночасних запусків.
3. Функція перевіряє значення, позначає аномалії і записує результат у базу MySQL (RDS).
4. Функція history (functions/worker/history.js) окремо читає історію з бази через HTTP-шлюз.

Дизайн: одна функція-диспетчер:

Обрано одну функцію processor, всередині якої є окремий обробник для кожного типу датчика (температура, вологість, освітленість). Причини:
- одна черга, один тригер і один набір прав доступу, менше інфраструктури;
- усі три типи мають однакову структуру повідомлення і пишуть в одну таблицю;
- обробка кожного типу коротка (кілька мілісекунд), окремі функції не дали б виграшу в масштабуванні.
Окрема функція на кожен тип була б доречна, якби типи мали різне навантаження, різні таймаути чи права або обробка була б важкою. Тоді повідомлення розділяли б по різних чергах або фільтрами тригера, і кожну функцію можна було б масштабувати окремо. Для нашого обсягу це зайва складність.

Дії для кожного типу:

Температура: якщо одиниця F, значення перераховується в C. Значення поза діапазоном від -50 до 60 C отримує статус out_of_range. Якщо значення відрізняється від попереднього вимірювання цього датчика більше ніж на 5 C, статус anomaly.
Вологість: значення поза діапазоном від 0 до 100 % отримує статус out_of_range.
Освітленість: якщо одиниця klx, значення перераховується в lux. Значення поза діапазоном від 0 до 100000 lux отримує статус out_of_range.
Усі інші повідомлення отримують статус ok. Статус і пояснення (note) зберігаються разом із вимірюванням, а повідомлення зі статусом, відмінним від ok, ще й виводяться в журнал функції.

Ідемпотентність:

Черга SQS гарантує доставку щонайменше один раз, тому те саме повідомлення може прийти двічі (наприклад, після таймауту або повтору відправника). Запис у базу захищений первинним ключем (sensor_id, measured_at) і запитом INSERT ... ON DUPLICATE KEY UPDATE sensor_id = sensor_id: якщо запис із таким ключем уже є, повтор нічого не змінює. Перевірка: те саме повідомлення надіслано чотири рази, у базі лишився один запис.

Що буває з повідомленням, яке не вдалося обробити:

Функція повертає результат у форматі ReportBatchItemFailures: в чергу повертаються лише ті повідомлення пачки, які не вдалося обробити, а решта підтверджується і видаляється. Повернуте повідомлення стає знову видимим через 60 секунд (visibility timeout). Після трьох невдалих спроб (maxReceiveCount = 3) воно автоматично переміщується в чергу недоставлених повідомлень (DLQ) cloud-lab3-measurements-dlq, де зберігається 14 днів для розбору. Так одне зіпсоване повідомлення не блокує обробку інших і не зациклюється.

Журнали:

Після кожної пачки функція пише в журнал один рядок {"processed":10,"failed":0}, а для кожного повідомлення зі статусом не ok і для кожної помилки окремий рядок. Дивитися: aws logs tail /aws/lambda/cloud-lab3-processor --since 10m --region eu-central-1
